How the training data is built
------------------------------

Each sweep CSV corresponds to one reservoir deck and one CPR solver
configuration label. The sweep runs multiple CPR configurations and logs one
row per Newton step with solver/state features and timing.

Typical feature columns include:

    dt_days
    dt_ratio
    nl_residual_norm
    nl_residual_reduce
    nl_iteration
    nnz_per_row
    diag_dominance
    prev_linsolver_iters
    prev_solve_failed
    time_elapsed_frac
    num_cells_log
    block_size

The sweep CSVs also contain total_ms, which is the timing used to decide which
configuration was best for a given Newton step.

collect_sweep_labels.py groups rows by:

    deck, episode, newton_iter

For each grouped Newton step, it compares all available CPR configurations and
chooses the configuration with the lowest median total_ms. That winning
configuration becomes the label.

So each ML sample is:

    solver/state features at this Newton step -> best CPR config label


How the sweeps and labels work
------------------------------

The sweeps are the data-generation step.

For each deck, Flow is run many times with different CPR solver configurations.
Each configuration gets a numeric label:

    00, 01, 02, ..., 23

During each run, Flow logs per-Newton-step data to CSV:

    features describing the current nonlinear/linear solve state
    total_ms timing for this CPR configuration
    config label

For example:

    SPE11A_09.csv

means:

    deck = SPE11A
    CPR config label = 09

There are 24 possible CPR configurations:

    3 pressure weight types
    x 2 CPR preconditioner types
    x 2 fine smoothers
    x 2 coarse smoothers
    = 24 labels

The label is computed as:

    label = weight_index * 8 + cprw_index * 4 + fine_index * 2 + coarse_index

The components are:

    weight_type:
        0 quasiimpes
        1 trueimpes
        2 trueimpesanalytic

    preconditioner:
        0 cpr
        1 cprw

    fine smoother:
        0 paroverilu0
        1 dilu

    coarse smoother:
        0 ilu0
        1 dilu

Example:

    label 09
    = 1*8 + 0*4 + 0*2 + 1
    = trueimpes + cpr + paroverilu0 + dilu

The CSV file's label is the configuration used for that run. It is not
automatically the final ML target. First, all available configurations are
compared for the same Newton step.

collect_sweep_labels.py groups rows by:

    deck, episode, newton_iter

Then, for each grouped Newton step, it asks:

    Which CPR configuration had the lowest median total_ms?

That winning configuration becomes the ML target label.

So the final supervised-learning row is:

    current solver features -> fastest CPR config label

The neural network therefore learns:

    Given the current Newton-step state, predict which CPR setup should be
    fastest.

The sweep data is supervised training data generated from brute-force timing
comparisons across CPR configurations.


Model training
--------------

train_cpr_policy.py trains a small neural classifier.

In the latest run, the data had:

    12 input features
    24 output classes

The 24 classes correspond to the CPR action space:

    3 pressure weight types
    x 2 preconditioner types
    x 2 fine smoothers
    x 2 coarse smoothers
    = 24 CPR configurations

bench_norne.sh tries hidden-layer sizes:

    8, 12, 16, 24, 32

and chooses the model with the best validation accuracy.

In the last full training attempt, the best architecture was:

    12 -> 24 -> 24
    validation accuracy about 0.241

The trained model is written to:

    /Users/macbookn/activopmwkspc/tmp/cpr_policy_retrained.model


How the model is used
---------------------

For neural runs, the script sets:

    OPM_NEURAL_CPR_WEIGHTS=/Users/macbookn/activopmwkspc/tmp/cpr_policy_retrained.model

Flow then loads this model and uses it inside NeuralCprPolicy to choose CPR
configuration actions during the simulation.

For SPE11A, the benchmark uses the existing SPE11 sweep solver config:

    /Users/macbookn/activopmwkspc/cpr_sweep_data/sweep_spe11/configs/label_09.json

with:

    --cpr-reuse-setup=0

This was needed because SPE11A was unstable with Flow's default solver setup.


Result consistency check
------------------------

For completed SPE11A baseline and neural runs, the physical summary outputs
were compared using ecl.summary.EclSum.

The physical results were very close where both methods completed or overlapped.
Example relative differences:

    FGIP   about 5.8e-05
    BWPR   about 1e-07
    RGIP:1 about 4e-04

So the neural policy changes solver behavior and runtime, but the physical
reservoir summary values look consistent over the compared interval.


Important caveat
----------------

Some longer SPE11A neural runs hit:

    Assertion failed: (isfinite(fluidState_.density(phaseIdx)))

This means not every SPE11A neural run completed successfully. The result
comparison is valid only over completed runs or over the overlapping time range
before an aborted run failed.
